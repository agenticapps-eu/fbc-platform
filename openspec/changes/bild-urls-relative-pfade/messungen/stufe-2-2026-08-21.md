# Stufe 2 gemessen (AGE-580)

2026-08-21, gegen den **lokalen Stack** (`supabase start`, DB 54322) — und damit
gegen echte Policies, echten Storage und die echte Migrationsdatei.

## 1. Die Sonde hat einen echten Fehler gefunden. Das ist ihr Wert.

`scripts/probe-age580-migration.ts` führt die **Datei** aus, nicht eine
Abschrift ihrer Logik, legt Fixtures an und rollt zurück. Erster Lauf:

```
  ok    eigene URL, Objekt liegt hier → zurückgeschnitten
  ok    eigene URL, Objekt liegt NICHT hier → unangetastet
FEHLER  FREMDE Supabase-Instanz, gleicher Bucket-Name → unangetastet
          soll: https://fremde-instanz.supabase.co/…/avatars/<uid>/a.webp
          ist : <uid>/a.webp
```

**Der zweite Entwurf war falsch, und er sah richtig aus.** Er antwortete auf
codex' HIGH-2 mit einer Existenzprüfung gegen `storage.objects` statt mit dem
Nennen des Hosts. Liegt unter demselben Pfad hier aber zufällig ein Objekt — und
bei gespiegelten Daten ist das der **Normalfall** —, greift die Prüfung ins
Leere und die fremde URL wird doch zerschnitten.

Damit ist codex' ursprüngliche Empfehlung vollständig bestätigt: eine einmalige
historische Migration darf ihren Host nennen. Jetzt sind es **zwei Riegel** —
Host UND Existenz —, und der zweite ersetzt den ersten nicht, sondern fängt den
anderen Fall (ein Wert, dessen Bild fehlt).

Nach der Korrektur, neun von neun:

```
  ok    eigene URL, Objekt liegt hier → zurückgeschnitten
  ok    eigene URL, Objekt liegt NICHT hier → unangetastet
  ok    FREMDE Supabase-Instanz, gleicher Bucket-Name → unangetastet
  ok    falscher Bucket in der Spalte → unangetastet
  ok    fremd gehostet (Demo-Seed) → unangetastet
  ok    schon ein Pfad → unangetastet (Wiederholbarkeit)
  ok    null → bleibt null
  ok    covers: eigene URL, Objekt liegt hier → zurückgeschnitten
  ok    wiederholbar: ein zweiter Lauf ändert nichts
```

**Die Gegenprobe ist bereits geführt:** ohne den Host-Riegel war Fall 3 rot. Der
Test hat Zähne, und zwar belegt, nicht behauptet.

## 2. Die Sichtprobe, die auf DEV nicht ging

Auf DEV scheiterte sie an der Anmeldung (neutralisierte Hashes seit dem
Spiegel). Lokal ging sie: Konto per GoTrue-Admin mit `email_confirm: true`,
aktiviert, `impact`, ein echtes Objekt im Bucket und der **Pfad** in der Spalte —
also genau der Zustand NACH der Migration.

### Alle drei Anzeigestellen, im Browser gemessen

| Stelle | Ergebnis |
|---|---|
| `<Avatar>` (Verzeichnis, Editor) | `…/avatars/<uid>/probe-avatar.webp`, **geladen** |
| `ProfileHero` (Profilansicht) | `…/covers/<uid>/probe-cover.webp`, **geladen** |
| `ProfilPage` Cover-Vorschau (`data-testid="cover-vorschau"`, Route `/profil/bearbeiten`) | **geladen** |

### Beide Formen nebeneinander — der Mischzustand der Umstellung

Im Verzeichnis rendern gleichzeitig:

- mein Probeprofil mit **Pfad** → aufgelöst, geladen,
- 20 Bestandsprofile mit **absoluter PROD-URL** → durchgereicht, geladen, 512×512.

Das ist genau der Zustand zwischen Migration und vollständiger Konvergenz, und
er trägt.

### Der `blob:`-Fall — durch den ECHTEN Hochlade-Fluss

Datei in den Eingang gelegt → Zuschneider öffnet („Hintergrundbild
zuschneiden") → „Übernehmen":

```
vorschau_src: "blob:http://localhost:5174/5ae694e0-…"
ist_blob: true · geladen: true · naturalWidth: 1500
```

**Das ist der Fall, den jsdom nie sieht** — es lädt kein Bild. Ein Auflöser, der
stur den Bucket-Host voranstellt, hätte die Vorschau still zerlegt, und jeder
Test wäre grün geblieben.

## 3. Der Erzeuger, gegen eine echte Datenbank

„Speichern" gedrückt — der echte `saveProfile` → `uploadBild` über den echten
Client und die echten RLS-Policies. Danach die Spalte gelesen:

```json
{ "avatar_url": "<uid>/probe-avatar.webp",
  "cover_url":  "<uid>/1787319246967.webp" }
```

Ein **Pfad**, keine Projektkennung. Und der Zweig ohne neues Bild hat den
vorhandenen Pfad in Ruhe gelassen.

Danach neu geladen: das frisch hochgeladene Cover rendert, **1500×500**. Der
volle Kreis: hochladen → Pfad in der Spalte → Auflöser → URL → Bild lädt.
